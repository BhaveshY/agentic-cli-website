What Is an AI Agent?
▼

Defining Agents

An AI agent is an autonomous software entity that perceives its environment, reasons about goals, and takes actions to achieve them. Unlike simple chatbots, agents maintain state, use tools, and make multi-step decisions.

Key Properties

  • Autonomy — Operates without constant human intervention
  • Reactivity — Responds to changes in its environment
  • Proactivity — Takes initiative toward goals
  • Social Ability — Interacts with other agents and humans
python
class Agent:
    def __init__(self, name, tools, memory):
        self.name = name
        self.tools = tools
        self.memory = memory
        self.state = "idle"

    def perceive(self, observation):
        # Process incoming information
        self.memory.store(observation)

    def reason(self, goal):
        # Plan next actions based on memory + goal
        context = self.memory.retrieve(goal)
        return self.plan(context, goal)

    def act(self, action):
        # Execute action using available tools
        tool = self.tools.get(action.tool_name)
        return tool.execute(action.params)
2
The Agent Lifecycle
▼

Perceive → Reason → Act Loop

Every agent operates in a continuous loop: it perceives its environment, reasons about what to do, and acts on its decisions. This loop forms the backbone of all agentic systems.

Lifecycle Phases

  • Initialization — Load configuration, tools, and memory
  • Observation — Receive input from environment or user
  • Planning — Determine the best course of action
  • Execution — Invoke tools and produce outputs
  • Reflection — Evaluate results and update memory
  • Termination — Conclude when goal is met or limits reached
python
async def run_agent_loop(agent, task):
    agent.state = "running"
    observation = task.initial_input

    for step in range(MAX_STEPS):
        # Perceive
        agent.perceive(observation)

        # Reason
        action = agent.reason(task.goal)
        if action.type == "finish":
            break

        # Act
        result = await agent.act(action)

        # Reflect
        agent.memory.store_reflection(action, result)
        observation = result

    agent.state = "complete"
    return agent.memory.get_final_answer()

Core Abstractions: Tools, Memory & LLM
▼

The Three Pillars

Every agentic harness relies on three core abstractions that must be engineered carefully:

  • LLM (Brain) — The language model that powers reasoning and decision-making
  • Tools (Hands) — Executable functions that let the agent interact with the world
  • Memory (Context) — Storage systems that maintain state across interactions

How They Connect

The harness is the glue that connects these three. It manages the flow of information between the LLM, tool calls, and memory reads/writes. Good harness engineering means making these connections reliable, observable, and extensible.

python
class AgentHarness:
    """The orchestration layer that ties everything together."""

    def __init__(self, llm, tools, memory):
        self.llm = llm           # Brain: reasoning engine
        self.tools = tools       # Hands: external actions
        self.memory = memory     # Context: state management
        self.hooks = []          # Observability callbacks

    def step(self, input_msg):
        context = self.memory.build_context(input_msg)
        response = self.llm.generate(context)

        if response.has_tool_call:
            result = self.tools.execute(response.tool_call)
            self.memory.store("tool_result", result)
            return self.step(result)  # Recursive loop

        self.memory.store("response", response)
        return response
4
Harness vs. Framework vs. SDK
▼

Understanding the Landscape

In the agentic ecosystem, terminology matters. Here's how to distinguish between common terms:

  • Harness — The runtime orchestration layer that manages agent execution, tool routing, memory, and safety. Think of it as the "operating system" for agents.
  • Framework — A library or toolkit (e.g., LangChain, CrewAI) that provides building blocks. You use frameworks within a harness.
  • SDK — A client library for interacting with specific APIs (e.g., OpenAI SDK). The lowest-level building block.

Good harness engineering means you can swap frameworks and SDKs without rewriting your orchestration logic.

Core Harness Components
▼

Anatomy of a Harness

A production harness consists of these key components:

  • Router — Dispatches messages to the right agent or sub-system
  • Executor — Manages the agent loop, retries, and timeouts
  • Tool Registry — Catalog of available tools with schema validation
  • Memory Manager — Coordinates short-term and long-term storage
  • Guard Rails — Safety checks that intercept inputs/outputs
  • Telemetry — Logging, tracing, and metrics collection
python
class HarnessConfig:
    router: Router
    executor: Executor
    tool_registry: ToolRegistry
    memory_manager: MemoryManager
    guardrails: list[GuardRail]
    telemetry: TelemetryBackend
    max_steps: int = 50
    timeout_seconds: float = 300.0

class Harness:
    def __init__(self, config: HarnessConfig):
        self.config = config
        self._running_agents = {}

    async def dispatch(self, request):
        agent = self.config.router.route(request)
        async with self.config.telemetry.span("dispatch"):
            return await self.config.executor.run(
                agent, request,
                tools=self.config.tool_registry,
                memory=self.config.memory_manager
            )

Design Patterns for Harnesses
▼

Common Patterns

  • Pipeline Pattern — Sequential processing through ordered stages
  • Router Pattern — Dynamic dispatch based on intent classification
  • Map-Reduce — Parallel agent execution with result aggregation
  • Supervisor — A meta-agent that delegates to specialized workers
  • Reflection Loop — Agent evaluates its own output and iterates
python
# Supervisor pattern: meta-agent delegates to workers
class SupervisorHarness:
    def __init__(self, supervisor, workers):
        self.supervisor = supervisor
        self.workers = {w.name: w for w in workers}

    async def run(self, task):
        plan = self.supervisor.plan(task)
        results = {}

        for step in plan.steps:
            worker = self.workers[step.agent_name]
            results[step.id] = await worker.execute(
                step.input, context=results
            )

        return self.supervisor.synthesize(results)

Error Handling & Resilience
▼

Building Robust Harnesses

Production agents fail in complex ways. Your harness must handle:

  • LLM failures — Rate limits, timeouts, malformed responses
  • Tool failures — External APIs down, schema mismatches
  • Infinite loops — Agent stuck in reasoning cycles
  • Resource exhaustion — Token limits, memory overflow
python
class ResilientExecutor:
    async def run_with_retries(self, agent, task):
        for attempt in range(self.max_retries):
            try:
                async with timeout(self.timeout):
                    result = await agent.run(task)
                    if self.validate(result):
                        return result
                    # Bad output — retry with feedback
                    task = task.with_feedback(
                        "Output failed validation, please fix."
                    )
            except RateLimitError:
                await exponential_backoff(attempt)
            except ToolError as e:
                task = task.with_feedback(str(e))

        raise MaxRetriesExceeded(task)

Observability & Telemetry
▼

Making Agents Debuggable

You cannot improve what you cannot measure. Instrument every layer:

  • Traces — End-to-end request flow through the harness
  • Spans — Individual operations (LLM call, tool execution)
  • Metrics — Latency, token usage, success rates, loop counts
  • Logs — Structured logs with correlation IDs

Use OpenTelemetry-compatible tracing so your agent runs show up alongside your regular application traces.

Building a Tool Registry
▼

Centralised Tool Management

The tool registry is the single source of truth for what an agent can do. It handles discovery, validation, execution sandboxing, and permission scoping.

python
class ToolRegistry:
    def __init__(self):
        self._tools = {}

    def register(self, name, fn, schema, permissions=None):
        self._tools[name] = Tool(
            name=name, fn=fn,
            schema=schema, permissions=permissions
        )

    def get_schemas(self, agent_role):
        # Return only tools the agent is allowed to use
        return [
            t.schema for t in self._tools.values()
            if t.permissions.allows(agent_role)
        ]

    async def execute(self, call):
        tool = self._tools[call.name]
        validated = tool.schema.validate(call.args)
        return await tool.fn(**validated)
3
MCP & External Tool Protocols
▼

Model Context Protocol (MCP)

MCP is an open standard for connecting agents to external tools and data sources. Instead of building custom integrations for every service, you use a standardised protocol.

  • Resources — Read-only data the agent can access
  • Tools — Executable actions with defined schemas
  • Prompts — Reusable prompt templates

Your harness should support MCP servers as first-class tool providers, enabling plug-and-play integrations.

4
Tool Error Handling & Sandboxing
▼

Safe Tool Execution

Tools interact with the outside world — files, APIs, databases. Every execution must be sandboxed with proper timeouts, resource limits, and error boundaries.

  • Always validate inputs against the schema before execution
  • Wrap tool calls in try/catch and return structured errors to the LLM
  • Apply rate limits per tool and per agent
  • Log every tool call for audit trail

Build the context management layer that gives agents persistent, relevant memory.

Intermediate
1
Short-Term vs. Long-Term Memory
▼

Memory Tiers

  • Working Memory — The current conversation/context window. Fast, ephemeral, size-limited by token budget.
  • Episodic Memory — Records of past interactions. Stored in a database, retrieved via search.
  • Semantic Memory — Distilled knowledge and facts. Vectorized for similarity search.
  • Procedural Memory — Learned workflows and patterns. Encoded as reusable prompts or code.
python
class MemoryManager:
    def __init__(self, working, episodic, semantic):
        self.working = working    # In-context messages
        self.episodic = episodic  # Past interactions DB
        self.semantic = semantic  # Vector store

    def build_context(self, query, token_budget=4000):
        # Combine memory tiers within token budget
        relevant = self.semantic.search(query, k=5)
        recent = self.episodic.get_recent(limit=10)
        working = self.working.get_messages()

        return fit_to_budget(
            working + relevant + recent,
            token_budget
        )
2
Vector Stores & Retrieval
▼

Embedding-Based Memory

Vector stores convert text into numerical embeddings and enable similarity search. This is the backbone of semantic memory for agents.

  • Embedding models — Convert text to vectors (e.g., OpenAI text-embedding-3-small)
  • Index types — HNSW, IVF, flat search — trade-off between speed and recall
  • Chunking strategies — How to split documents for embedding (sentence, paragraph, semantic)
  • Metadata filtering — Combine vector search with structured filters
3
Context Window Management
▼

Token Budgeting

The context window is the most precious resource. Harness engineers must carefully manage what goes in:

  • System prompt + instructions (fixed cost)
  • Tool schemas (scales with tool count)
  • Retrieved memory (dynamic, query-dependent)
  • Conversation history (grows over time, must be trimmed)
  • Reserve space for the model's response

Implement a token budget allocator that dynamically balances these components.

Memory Persistence Patterns
▼

Saving State Across Sessions

Agents that remember across sessions are dramatically more useful. Common patterns:

  • Conversation summaries — Compress old messages into summaries
  • Fact extraction — Pull out key facts and store as structured data
  • User modeling — Build a profile of user preferences over time
  • Task journaling — Record what was attempted, what worked, what failed

Module 5: Multi-Agent Orchestration

Coordinate multiple specialized agents working together on complex tasks.

Why Multi-Agent?
▼

When One Agent Isn't Enough

Complex tasks benefit from specialized agents that each excel at one thing. Benefits include:

  • Each agent has a focused system prompt and tool set
  • Smaller context windows per agent = better reasoning
  • Parallel execution for independent sub-tasks
  • Easier testing — each agent is a unit

The harness orchestrates communication, shared memory, and conflict resolution between agents.

2
Communication Patterns
▼

Agent-to-Agent Communication

  • Direct messaging — Agent A sends a structured message to Agent B
  • Shared blackboard — Agents read/write to a shared state store
  • Event bus — Pub/sub for loose coupling between agents
  • Supervisor handoff — A coordinator passes context between workers
python
class AgentBus:
    def __init__(self):
        self._subscribers = defaultdict(list)

    def subscribe(self, topic, agent):
        self._subscribers[topic].append(agent)

    async def publish(self, topic, message):
        for agent in self._subscribers[topic]:
            await agent.receive(message)

# Usage in harness
bus = AgentBus()
bus.subscribe("code_review", reviewer_agent)
bus.subscribe("code_review", security_agent)
await bus.publish("code_review", code_diff)

Conflict Resolution & Consensus
▼

When Agents Disagree

Multiple agents may produce conflicting outputs. Strategies:

  • Voting — Majority wins among parallel agents
  • Ranked authority — Higher-priority agent's output wins
  • Debate & synthesis — Agents argue, a judge synthesizes
  • Human-in-the-loop — Escalate to a human when confidence is low

Scaling Agent Systems
▼

Production Considerations

  • Agent pooling — Reuse agent instances across requests

  • Queue-based dispatch — Use message queues for load balancing
  • State isolation — Ensure agents don't leak state across tasks

1
Input & Output Guardrails
▼

Defense in Depth

Guardrails are middleware that intercept inputs and outputs at every stage:

  • Input validation — Block prompt injection, PII leaks, off-topic requests
  • Output filtering — Catch hallucinations, harmful content, data leaks
  • Tool call validation — Ensure tool arguments are safe and within scope
  • Response grounding — Verify claims against source documents
python
class GuardrailPipeline:
    def __init__(self, guards):
        self.guards = guards

    async def check_input(self, msg):
        for guard in self.guards:
            result = await guard.check_input(msg)
            if result.blocked:
                return BlockedResponse(
                    reason=result.reason
                )
        return PassedResponse()

    async def check_output(self, output, sources):
        for guard in self.guards:
            output = await guard.filter_output(
                output, sources
            )
        return output
2
Evaluation Frameworks
▼

Measuring Agent Quality

You need automated evaluation to iterate on agent quality:

  • Task completion rate — Did the agent achieve the goal?
  • Tool call accuracy — Were the right tools called with correct args?
  • Efficiency — Steps/tokens used vs. optimal path
  • Safety score — Did any guardrails trigger?
  • User satisfaction — Thumbs up/down, CSAT from real usage

Build eval suites as part of your CI/CD pipeline. Run them on every prompt or model change.

3
Testing Agent Harnesses
▼

A Testing Pyramid for Agents

  • Unit tests — Test individual tools, memory operations, guardrails in isolation
  • Integration tests — Test the harness with mocked LLM responses
  • End-to-end tests — Full agent runs against real (or simulated) environments
  • Regression tests — Golden datasets of known-good agent trajectories
  • Chaos tests — Inject failures (tool errors, timeouts) and verify graceful degradation
4
Responsible AI & Governance
▼

Beyond Technical Safety

Production agentic systems need organizational governance:

  • Clearly define what agents are allowed to do (scope boundaries)
  • Implement audit logs for every agent action
  • Require human approval for high-risk operations
  • Document agent capabilities and limitations for end users
  • Establish incident response procedures for agent failures
